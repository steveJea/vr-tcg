## 안전장치

- 매 파일 시작에 현재 DB의 `pg_control_system().system_identifier::text`가 지정된 **7703759698107299042**와 정확히 같은지 확인합니다. 다르거나, NULL이거나, 조회 권한/기능 오류가 나면 중단합니다. guard를 삭제하거나 임의 SET/번호 변경으로 우회하지 마세요.
- SQL Editor가 실제 `project_ref`를 SQL 변수로 제공한다고 가정하지 않습니다. `confirmed_ref`는 테스트 ID로 고정하고 실제 DB 식별번호도 함께 검사합니다.
- 클러스터 번호는 프로젝트 이름 그 자체는 아니며 복제 DB에서 같을 수 있습니다. 따라서 화면의 프로젝트 선택 확인, 최초 설치 시 기존 사용자/게임 테이블·함수 거부, 이후 비공개 설치 기록·번호 순서 검사도 함께 사용합니다. 운영 선택을 허용하는 옵션은 없습니다.
- 새 프로젝트 전용입니다. 운영 회원/결제 자료는 포함하지 않으며, 원본 관리자 판정 규칙을 유지하고 마지막에 보안 1단계를 적용합니다. 미검증 전투 보상 보류 범위를 먼저 확인하세요. 모든 보안 취약점이 해결된 것은 아닙니다.

## 재실행과 오류

- 같은 파일을 다시 실행하면 비공개 설치 기록을 보고 변경 없이 건너뜁니다. 최신 함수가 옛 함수로 되돌아가거나 기존 진행 자료가 초기화되지 않습니다.
- 앞 파일이 빠졌거나 서로 다른 버전의 파일을 섞으면 중단합니다. 같은 커밋의 파일만 사용합니다.
- 각 파일은 한 트랜잭션입니다. 실패한 파일의 변경과 설치 기록은 함께 되돌아가며, 먼저 성공한 파일은 유지됩니다.
- 오류가 나면 번호와 오류 내용을 확인하고 그 파일부터 다시 진행합니다. 설치 기록을 지우거나 운영/기존 DB에서 시작하지 않습니다.
- 설치 도중에는 API 계정의 `public` 스키마 사용을 차단하고 마지막 파일까지 성공한 뒤 엽니다. 마지막 검사는 함수 재컴파일·RLS·내부 함수 권한·사용자 자료 없음입니다.
- SQL Editor가 연결을 끊었다고 나오면 새 편집기에서 해당 파일 전체를 다시 실행합니다. 같은 세션에서 이미 실패한 트랜잭션이라는 오류가 계속될 때만 `ROLLBACK;`으로 실패 상태를 끝낸 뒤 해당 파일 전체를 다시 실행합니다.

## 개발자 재생성·검증

```bash
node tools/build_staging_parts.mjs
npm run test:staging
```

WASM PostgreSQL에서는 로컬 DB 식별번호를 메모리에서 테스트용으로 바인딩해 전체 순서 설치, 각 파일/완료 후 역순 재실행, 설치 후 계정/진행 자료 보존, 순서·버전·운영 확인 문자열·다른 DB 차단, 중간 실패 롤백을 검사합니다. 배포 파일의 19자리 값과 문자열 형식도 검사합니다. 실제 Supabase에 SQL을 실행한 것은 아니며 Google 로그인·메일·휴대폰 동작 확인은 별도입니다.

옛 통합 파일 `supabase/staging_install.sql`은 개발 검사용으로 유지합니다. SQL Editor에는 그 큰 파일을 다시 붙이지 마세요.
