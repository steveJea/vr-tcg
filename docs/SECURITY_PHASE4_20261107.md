# 보안 4단계 — 토벌 / 조직전 (staging 전용)

운영 배포는 전체 보안 작업이 끝날 때까지 보류한다. 이 변경은 운영 Supabase/Worker에 적용하면 안 된다.

## 스테이징 적용 순서 (기존 DB)

1. Supabase에서 **cuyqchmdcnsgzkwyclji** 테스트 프로젝트인지 확인한다.
2. SQL Editor에서 `supabase/security_phase4_raid_guildwar.sql` **전체**를 실행한다. DB 고유번호 `7703759698107299042`가 아니면 자동 중단한다. Guard를 지우지 않는다.
3. Edge Functions에서 **guildbattle-verify-v4**를 새로 만들고, `supabase/functions/guildbattle-verify-v4/dashboard_single_file.ts` **전체**를 `index.ts`에 붙여 배포한다. JWT verification은 **ON**. 별도 키/토큰 입력은 필요 없다. Supabase가 제공하는 런타임 `SUPABASE_*` 환경변수만 사용한다.
   - CLI 사용 시 `supabase functions deploy guildbattle-verify-v4 --project-ref cuyqchmdcnsgzkwyclji` (이 작업에서 실행하지 않음).
   - `_shared/guildbattle-engine-v4.mjs` + `index.ts` + `handler.mjs`를 CLI로 배포하는 방법과 단일 파일 방법의 코드는 동일하다.
4. 이 브랜치의 클라이언트를 **staging Worker에만** 배포하고 PC Chrome에서 강력 새로고침한다. SQL → Edge → 클라이언트 순서다.
5. 아래 seed를 실행하고 토벌/조직전에 들어가 본다.

기존 DB에 `staging_install.sql`이나 `supabase/staging/*_install.sql`을 다시 실행하지 않는다. 이들은 **빈 신규 테스트 DB** 전용 재생성본이다.
기존 PvP 함수는 바꾸지 않았다. phase3 엔진 해시 `ff3c2c77…`와 `pvp-verify-v3/dashboard_single_file.ts`는 그대로다. 이전 PvP 레벨 수정 배포가 아직 안 됐다면 그 단계의 SQL/Edge도 먼저 적용해야 한다.

## 두 모드를 지금 테스트하는 seed / refill / reset

`supabase/staging_seed_raid_guildwar.sql`:

1. **전용 테스트 계정 2개**로 로그인하고 두 계정 모두 스토리 시작 인재를 고른다. 실제 사용하는 조직에 가입된 계정은 쓰지 않는다.
2. Dashboard Authentication → Users의 두 UUID를 SQL의 `user_a`, `user_b`에 넣는다. 비밀번호/키는 넣지 않는다.
3. `action := 'start'`로 전체 SQL을 실행한다.
4. 두 계정으로 각각 접속한다. `SEC4_TEST_…` 비공개 조직의 보스로 들어가고, `SEC4 TEST` 덱/전쟁 공격1·방어1이 준비된다. 토벌은 바로 전투, 조직전은 적 방어조 1~5 중 하나를 선택한다. 행동력이나 참가 티켓은 필요 없다. 토벌 **하루 3회**, 조직전 **하루 5회** 제한은 그대로다.
5. **진행을 유지하고 횟수만 채우려면 `action := 'refill'`**로 전체 SQL을 다시 실행하고 게임을 새로고침한다. 아래 절차 참고. **처음부터 새 경기**를 하려는 경우에만 `action := 'reset'`으로 다시 실행한다. **다음 가상 시즌/주**를 새로 열어 횟수·보스·매치를 새로 만든다. 기록을 삭제하거나 지갑/우편/보상 원장을 되돌리지는 않는다. 누적 테스트 보상은 남는다. 새로고침하면 이전 예약의 무효 영수증이 정리된다.
6. 끝나면 `action := 'stop'`으로 실행한다. 실제 KST 시간으로 복귀한다. 원래 기록/테스트 카드/조직은 삭제하지 않는다.

Seed가 만드는 것:
- 기존 Auth 계정만 사용. 계정 생성/임의 로그인/기존 조직 탈퇴 없음.
- 계정당 태그가 붙은 Lv80 카드 5장과 스토리 덱 1개. 기존 카드는 보존한다.
- 지정한 테스트 계정의 전쟁 덱은 공격1·방어1=테스트 덱, 공격2·방어2=빈 덱으로 설정한다.
- Lv3 비공개 조직 2개, 보스/조직원 소속과 가입 시각, 활성 토벌 보스 행, 조직전 시즌/명단/상대 조직/매치/전투 창.
- 가상 시각: 해당 테스트 월의 **셋째 수요일 12:00 KST**부터 실제 시간만큼 진행. **실제 4시간 후 자동 해제**. `start` 재실행은 시간 창만 연장하며 기록/횟수를 초기화하지 않는다. 토벌·조직전 이외의 시간 함수는 바꾸지 않는다. 테스트 시계가 켜진 동안 조직전 자동 참가는 지정된 두 조직만 대상으로 한다.
- 다른 실사용 staging 계정과 동시에 시험하지 않는다. 시계 변경은 staging 토벌/조직전 전역에 영향을 준다.

### 방어조 전멸 → 다음 조 공격을 혼자 계속 시험하기

**5회로는 부족하다.** 기본 fixture의 적 방어조는 **5곳 × 2덱 = 최소 10승**이다. 첫 덱을 깨도 둘째 덱이 남아 있으면 그 거점은 아직 살아 있다. **5곳 모두 완전히 파괴되어야** 공격조·중간보스·보스 등이 열린다. 방어조를 남긴 채 다음 조를 선택하면 서버도 `defense first`로 거부한다.

1. 현재와 **같은** `user_a`, `user_b` (동료를 넣었다면 같은 `allies_a/b`)를 유지한다.
2. `action text := 'refill'`로 바꾸고 **파일 전체**를 staging SQL Editor에서 실행한다.
3. 게임을 새로고침한다. 토벌 **3회**, 조직전 **5회**로 돌아온다. 남은 방어조의 두 번째 덱까지 계속 깬다.
4. 횟수가 다 되면 **refill을 반복**한다. 10승으로 방어조가 다 깨진 뒤에도 횟수가 0이면 한 번 더 refill하고 **공격조 6번** 등을 눌러 본다. **reset을 쓰면 새 경기라 방어조가 되살아난다.**

이미 phase4 SQL/Edge가 설치된 staging이면 **새 seed 파일만 실행**하면 된다. 파일 안에 private 충전 장부/동일한 서버·표시 한도 함수를 설치하므로 큰 phase4 SQL을 다시 실행하거나 Edge/Worker를 재배포할 필요가 없다. DB 고유번호·기존 phase4 엔진 버전이 다르면 전체 롤백한다.

`refill`은 현재 가상 시즌·주·날짜·매치·양쪽 HP·파괴 상태·공격덱 HP·점수·토벌 보스·카드/덱·재화·시계의 시작/만료/실행번호를 **바꾸지 않는다**. 기존 전투/보상/소탕 증거를 삭제하거나 날짜/매치를 옮기지 않고, operator-only 기준점 장부만 남긴다. 반복 실행해도 횟수가 3/5를 넘게 쌓이지 않는다. 지정 계정의 미완료 전투만 무보상 무효 영수증으로 닫고 예약을 해제한다. 늦은 결과 전송은 HP/보상을 바꾸지 못하며 새로고침 시 정리된다.

충전 기준점은 **이 staging DB + 같은 활성 시계/run + 같은 날/매치 + 같은 fixture 조직/계정**에서만 적용된다. 만료·stop·reset·소속 변경에는 적용되지 않으며 일반 계정의 한도나 방어조 게이트는 열지 않는다. 만료/경기 종료 상태면 refill은 거부하고 시계도 연장하지 않는다. 내 공격덱 전멸/내 아지트 파괴도 되살리지 않는다. 자동 검증에서 **동일한 Lv80 HR 공격덱의 누적 HP를 유지한 채 10개 NPC 방어덱 승리 → 게이트 개방 → 공격조 6번 실제 서버 전투 발급/정산**을 확인한다.

**동시/협동 시험(선택):** `allies_a`에 전용 계정 UUID **2개**를 추가하면 A조직 3명(기본 합계 15회)이 된다. 이 계정들도 시작 인재 선택·다른 조직 미가입 조건이 필요하며 같은 테스트 카드/덱을 받는다. B조직은 `allies_b`. 이 동료를 충전하려면 refill 때도 같은 명단을 넣는다. (명단에서 빼면 그 계정의 시도·예약은 건드리지 않는다.)

## 권위와 규칙

- 예전 `raid_finish(damage)` / `war_finish(win, HP)` / 별도 `*_log` 및 모든 오버로드·직접 테이블/열 쓰기 경로를 닫는다.
- 시작 RPC는 소속/전투 시간/명단/대상/공격권/살아있는 덱을 확인하고 seed·덱·레벨/EX/boost/기술/장비·역할 보너스·이전 HP를 서버에서 동결한다. guest/대여 카드는 **기존처럼 금지**한다.
- 저장된 전쟁 덱의 오래된 능력치를 그대로 쓰지 않는다. 방어는 시즌 명단 잠금 시, 공격은 그날 해당 덱 최초 사용 시 현재 소유 UID로 다시 스냅샷한다. 발급 후 카드/장비가 바뀌어도 그 전투는 동결값으로 재생한다.
- 화면 AUTO/PLAY 전환이 가능하면 실제 구체 행동 목록(`atk/skill/end`)을 제출한다. 화면 없는 AUTO는 행동 없이 서버가 처음부터 실행한다. 클라이언트의 피해/승패/잔여 HP는 전송하지 않는다.
- 서버는 브라우저와 동일한 `raid-core`/`war-core`/`pvp-core`, 카드/NPC/기술 데이터를 실행한다. 누락/추가/불법 행동은 거부한다. 범용 permissive `replay()`를 검증에 사용하지 않는다.
- 토벌: 기존 15 내 턴, 타격 상한/약점, 난이도, 공유 HP 및 **초과 피해 다음 단계 이월** 규칙을 유지한다. 같은 단계에서 발급된 공격들은 시작 보스 기준으로 계산한 피해를 정산 시 공유 보스에 순서대로 적용한다. 마지막 일격/단계 보상은 잠금 안에서 한 번만 기록한다.
- 토벌 소탕: **현재 조직·같은 주·같은 날의 검증 완료 직접 전투 최고 피해 90%**만 사용. 과거 미검증 기록/타 조직 기록은 불가. 서버 UUID 영수증으로 재시도 시 중복 차감/지급 없음.
- 조직전: 방어조 5곳 우선, 두 번째 방어 덱, 누적 HP, 역할 점수, 보스 격파 즉시 경기 종료, 23:00 KST 정산 규칙 유지. 기본 엔진의 40턴 판정 승리도 기존처럼 해당 방어 덱 격파로 처리한다(단순 HP 0만 승리 조건이 아님).
- 공격자 아지트 생존 자격은 발급 시 확인한다. 도중에 내 일반 아지트가 파괴되어도 이미 발급한 공격은 계속할 수 있다. 경기 종료/정산/기간 변경/대상 상태 변경/소속 변경 후 제출은 **무효·0지급**, 예약 횟수는 돌려주지 않는다.
- 같은 대상은 전투 만료와 맞춘 **20분 예약**(예전 3분에서 확대). 정산 때 예약 주인+이전 HP+방어 덱을 다시 비교하여 오래된 결과가 새 HP를 덮어쓰지 못한다. 새 공격을 시작하면 이전 미완료 공격은 무보상 포기 처리된다.
- 지난 시즌의 미정산 매치를 먼저 마감한 뒤 시즌 순위를 계산한다. 시즌 종료 뒤 소급 명단 등록은 금지한다. 정산된 모든 5일 경기 없이 시즌 순위 보상을 수령하지 못한다.
- 경기/시즌 조직전 보상은 기존처럼 **동결된 명단의 권리**다. 이후 탈퇴했어도 수령 가능하되 시즌당 유저 명단은 하나이고, 전역 개인 claim key로 중복 불가. 토벌 단계·주간 보상은 현재 같은 조직·기존 가입 시각 조건을 유지한다.
- 전쟁에서 공격하지 않은 참가자의 정규 무승부/시즌 참여 보상은 원래 규칙처럼 서버 시간 정산 이력으로 설명된다. 플레이어가 승리를 신고해서 생기는 보상이 아니다.

### staging에서 확인 후 승인할 정책 차이

1. 과거 미검증 피해/점수를 승격하지 않기 위해 **새 v4 공식 누적/순위 공간**을 사용한다. 원본 표/재화/우편은 보존한다. 전쟁 덱 설정만 복사하고 UID로 재검증한다. 옛 미검증 결과에서 새 보상을 주지 않는다.
2. 토벌 난이도는 피해가 0이어도 **시도가 발급된 뒤에는 변경 금지**한다.
3. 전쟁 예약은 20분, 종료 후 소급 명단 등록 및 소속 변경 후 정산은 금지한다.
4. 주간 토벌 참여 보상은 해당 조직에 검증된 양수 피해가 있을 때만 열린다(상태 조회만으로 보상 생성 방지).

이 정책들은 staging 검증 대상이며, 운영 적용 전에 소유자 승인이 필요하다.

## 보상 / 나머지 보류

새 공식 결과/수령은 v4 세션·이벤트·시도와 `reward_claims`, `guild_claims` 및 각 재화 원장에 원자적으로 연결된다. 토벌 장비/단계·주간 상자/증표 우편 트리거도 같은 트랜잭션이다. 글로벌 옛 `_guild_reward`/배틀 feed는 재개하지 않는다.

토벌 의뢰만 검증 직접전투+서버 소탕 영수증으로 진행/수령한다. 옛 `q.progress`/기여도는 근거가 아니다. 다른 미검증 조직 의뢰, 일일 3개 전체 보너스, 도감/MVP 같은 후속 보류 기능은 임의 재개하지 않는다. 이 단계가 전체 보안 완료/운영 배포 승인을 뜻하지 않는다.

## 확인 목록

- PC Chrome: 두 계정에서 토벌 AUTO/수동 → 서버 피해 표시, 3회 제한, 소탕 90%, 새로고침/네트워크 재시도 시 중복 지급 없는지.
- 조직전 AUTO/PLAY 전환, MR 영상 후 정상 진행, 실제 HP 유지·두 번째 덱·방어조 게이트·보스 종료. refill 반복 또는 동료 계정으로 계속 진행.
- 여러 PC/탭: 동시 토벌 마지막 일격·초과 이월, 같은 전쟁 대상 예약, 같은 공격 재전송 시 점수/HP/보상 한 번만 반영.
- 전투 중 탈퇴/기간 종료/시계 stop, 대상 HP 변경 후 제출, 23:00 KST 이후 제출은 무효. 슬롯/카드 소유권/가짜 결과/extra action 조작 거부.
- 단계/주간/경기/시즌 수령, 반복 클릭/길드 이동 후 재수령, 토벌 의뢰·장비/우편 중복 없음.
- 모바일 화면은 추가 수동 확인 권장. 이 작업에서 live Supabase/브라우저를 조작하거나 배포하지 않았다.

긴급 중단: **staging DB에서만** `update public.guildbattle_policy_v4 set enabled=false where singleton;` 신규 시작/정산 지급/수령을 닫는다. 기존 무효/포기 영수증 조회는 가능. SQL 재실행해도 이 중단 플래그는 유지된다. 구버전 SQL로 되돌려 취약한 RPC를 다시 열지 않는다.

## 재현 검사

`npm run check:staging`, `npm run test:staging`, `npm run build:staging`, `npm run test:security:phase1`부터 `phase4`까지.
Phase4는 브라우저/서버 AUTO·수동·view 64개 엔진 조합, 실제 Edge 및 생성 Dashboard + PGlite, 권한/해당 계정/중복/만료/소속 변경/오래된 HP/한도/소탕/의뢰/중단/트랜잭션 rollback/seed-reset 및 기존 DB standalone refill 업그레이드·상태 보존·충전 한도/스코프·늦은 결과·실제 10승 후 다음 조 발급을 포함한다. 실제 Postgres 다중 연결 경합과 PC 화면 시험은 위 staging 목록으로 별도 확인한다.
