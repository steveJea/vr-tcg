- 조직전 정산은 시각이 됐다고 별도 cron이 즉시 지급하는 방식이 아니라, **상태 조회/보상 수령 등의 RPC가 `_war_tick()`을 호출할 때** 실행됩니다. 수령도 별도입니다. 과거 미정산 경기/미수령 보상이 있으면 preflight 결과와 기존 화면에서 먼저 확인합니다.
- **권장 이관 후보: 2026-11-08(일) 23:00 KST 이후 점검 시작, 2026-11-09(월) 00:00 KST 새 토벌 주간이 열리기 전 완료 목표.** 토벌의 22:05 KST 결과 마감과 보상 수령에 여유를 둔 운영 제안이며, 코드상 강제 이관 시각은 아닙니다. 23시가 되어도 정산/수령·백업·실행 직전 preflight 확인이 안 끝났으면 실행하지 않습니다.
- 이 창을 놓치면 새 주간의 구버전 토벌 진행이 생기지 않도록 점검을 유지하거나 새 전환 시점을 다시 정해야 합니다. 보상 수령이 끝나지 않았는데 시간에 맞추려고 강행하지 않습니다. 형님 preflight 회신상 조직전 미정산은 0이나, 미수령 보상 현황과 점검 직전 진행 중 건수는 별도 확인해야 합니다.
- 근거: 기존 운영용 [토벌 종료](../supabase/guild3.sql#L57-L58)·[결과 마감](../supabase/guild3.sql#L198-L212)·[주간 보상 조건](../supabase/guild3.sql#L231-L258), [조직전 월간 일정](../supabase/guild4.sql#L70-L92)·[실제 tick 정산](../supabase/war_auto.sql#L46-L61). 새 운영 delta에도 같은 달력/종료 시각을 사용합니다([v4 달력](../supabase/security_phase4_raid_guildwar.sql#L295-L317), [v4 시즌 보상 조건](../supabase/security_phase4_raid_guildwar.sql#L548-L563)). 해당 SQL 달력 함수를 로컬 PostgreSQL/WASM에서 실행해 위 날짜를 확인했습니다.

## 3. 기존 사용자 — 유지되는 것 / 확정 정책

### 유지
- 계정·세이브·인재·레벨·강화·지갑(유/무료 젬 포함)·기존 수령 장부는 삭제/초기화하지 않습니다. EXP/레벨 보정도 없습니다.
- 기존 스토리 클리어/탑 최고·지급 층은 **접근/중복 보상 차단용 동결 기준**으로 보존합니다. 옛 JSON 별/승리 수가 새 보상 증빙으로 자동 승격되지는 않습니다.
- 기존 조직 소속은 유지합니다. 전쟁 덱 설정은 v4로 복사하고 실제 사용 때 소유 인재 기준으로 갱신합니다. 새 기록과 구기록을 섞어 보상하지 않습니다.
- 같은 서버 영수증을 재전송해 보상/미션/랭킹이 중복 오르지 않습니다.

### 형님 확정 정책 — 2026-11-08 KST (t2602u)
1. **기존 계정에도 새 레벨 제한 적용.** grandfathering/기존 사용자 예외를 두지 않습니다. 조건 미달이면 과거 이용하던 메뉴도 잠깁니다. 계정 EXP/레벨을 보정하지 않습니다.
2. **공식 기록 새 출발 승인.** PvP 공식 레이팅은 1000에서 시작하고 아케이드 공식 기록/검증 승리 수는 새 기록만 집계합니다. 옛 데이터는 남지만 공식 순위·새 미션 근거가 아닙니다. 기존 시즌/티어 수령 장부를 지워 중복 지급하지도 않습니다.
3. **이번 주 정산 후 토벌/조직전 전환, 덱만 이월 승인.** 옛 주간 토벌 HP/피해·전쟁 점수/명단/아지트 HP·미수령 보상은 v4로 자동 이월하지 않습니다. 기존 보상을 먼저 정산/수령한 뒤 위 점검 창에 전환합니다. 데이터 보존과 진행 이월은 다릅니다. 조직전은 이번 주 비시즌이므로 과거 잔여 건 유무를 별도 확인합니다.
4. **기존 사용자도 안내/해금 보상 1회 지급 승인.** 조건 충족/필요한 짧은 체험 후 아직 받은 적 없는 안내 보상을 한 번씩 받을 수 있습니다. 설치 순간 지급하지 않습니다. 최대 전체 안내 기준 금화 45,000·순수한 피 5,000·각성자의 혼 1,000·소환권 20·상자 6·증표 선택상자 10(챕터/체험 조건 포함)입니다. 서버 수령 장부로 중복을 막습니다.

네 정책은 현재 staging/준비 SQL 동작과 같아서 이 문서 갱신만으로 확정했습니다. **운영 DB 고유번호는 확인·고정됐고, 남은 설치 선행조건은 실제 정산·수령/점검 준비입니다.** 형님이 실행한 것은 **운영 프로젝트의 읽기 전용 preflight**가 맞으며, `01_install.sql` 실행이나 main 병합이 자동으로 진행되는 것은 아닙니다.

## 4. 남아 있는 보안/운영 위험

- **보안 2단계는 완전 결정적 전투 재현이 아닙니다.** 스토리/탑/특강은 서버 세션+순서/시간/범위/보상 자격 검사(plausibility-v3)입니다. PvP/토벌/조직전/아케이드의 엄격한 행동 재현과 같은 보증이라고 말할 수 없습니다.
- 도감/MVP 지급과 일부 미검증 조직 의뢰·전체 보상 등 **기존 보류는 전부 풀지 않습니다.** 5단계가 다시 여는 것은 검증 아케이드 미션/일반 일일·주간 전체 보상입니다. phase1–5 통과가 남은 전체 보안 감사 완료를 뜻하지 않습니다.
- 형님이 운영 DB 식별/진행 건수 preflight는 확인했습니다. 다만 운영 전체 스키마/데이터 분포·Deno/JWT gateway·네트워크·Postgres 동시성은 아직 검증하지 않았습니다. 실행 직전 preflight를 다시 확인하며, 설치본은 누락 선행/예상 밖 엔진이면 중단합니다.
- 배포 실패 시 **옛 클라이언트만 main으로 되돌리면 해결되지 않습니다.** DB가 이미 옛 완료 경로를 차단합니다. 점검을 유지하고 forward-fix/검토된 백업 복구를 선택해야 합니다. 순위/지급 중 운영 DB를 무작정 롤백하지 않습니다.

## 5. staging 전용 요소가 운영에 섞이지 않는지

- `js/config.js`와 `wrangler.toml`은 기준 main과 staging 간 차이가 없습니다. `tcg.mbbs.kr`은 운영 Supabase로만 연결하고 TEST 배지를 만들지 않습니다. querystring으로 운영을 staging으로 바꿀 수 없습니다. 미등록 호스트는 비활성입니다.
- Worker 설정은 staging 호스트/`.staging-dist`만 대상으로 합니다. GitHub Pages main 배포에서 실행되지 않습니다. 이 작업은 `deploy:staging`/wrangler나 운영 배포를 실행하지 않았습니다.
- staging seed/clock/refill 파일은 안전한 별도 테스트 자료로 저장소에 남지만 런타임에서 import/호출하지 않습니다. DB 고유번호도 staging으로 고정되어 운영에서 실행 거부됩니다. **운영 delta에는 시계 테이블/테스트 길드/seed/refill 기능을 아예 넣지 않았습니다.**
- 운영 `_guildbattle_now_v4()`는 실제 `now()`만 쓰고, 실제 조직 참가 조건을 사용하며, 횟수는 기존+새 시도를 합산해 3/5 제한을 유지합니다. 테스트용 추가 횟수/고정 시즌은 없습니다.
- 기존 원본 staging Edge 파일은 그대로 유지했습니다. 운영 전용 생성본은 목적지/오류 라벨/헤더만 변경하며 엔진 바이트·해시는 같습니다. 재생성 드리프트 검사가 있습니다.

## 7. 자동 검사/재생성

`npm run check:staging`, `npm run test:staging`, `npm run build:staging`,
`npm run test:security:phase1` ~ `phase5`, `npm run test:production`.

운영 검사는 네트워크/실제 키 없이 PostgreSQL/WASM의 **기존 사용자 있는 레거시 DB**에서 실행합니다.

접근 기준·덱 복사, 재실행 no-op/비상 정지 보존, 내부 권한, 테스트 기능 제거,
